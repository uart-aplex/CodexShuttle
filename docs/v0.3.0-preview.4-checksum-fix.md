# v0.3.0-preview.4: Non-Mutating SQLite Inspection

Date: 2026-10-16. Supersedes preview.3 for package inspection and restore.

## Incident and Cause

A replacement restore failed checksum validation on `thread_history_1.sqlite-shm` before copying destination files. Full comparison found one mismatched SHM cache out of 3,335 checksummed files. The database and committed WAL still matched the original hashes.

The preceding diagnostic had opened the packaged database with SQLite `ReadOnly` mode. This prevents database writes but does not guarantee that the accompanying SHM file remains unchanged. SQLite can write shared-memory read marks or rebuild the WAL index even for read-only database connections. The earlier assumption that a read-only SQL diagnostic was byte-preserving was incorrect. See the official [WAL format](https://sqlite.org/walformat.html) and [temporary file documentation](https://sqlite.org/tempfiles.html).

SHM is a derived shared-memory index. WAL is different: it may contain committed conversation data absent from the main database and must not be discarded or ignored.

## Fix

- Before read-only SQL inspection, copy only the database and any WAL/rollback journal to a unique local temporary directory. Do not copy SHM; SQLite builds its private cache there.
- Hold read-only file handles denying writes while copying the quiescent input. An active writer causes failure rather than a potentially inconsistent inspection. Close Codex before applying restore or merge.
- Inspect the temporary database through SQLite, retaining committed WAL visibility. Do not use `immutable=1` as a shortcut to bypass WAL handling.
- Apply the same isolation to merge source inspection and destination preview. Intentional destination repair/merge writes retain their existing explicit write path.
- Remove temporary inspection files when their scope ends. This is a database-only inspection copy, not an extra workspace snapshot or a USB pre-restore copy.
- Keep checksum verification strict, including SHM. No blanket exception or automatic checksum regeneration was introduced.

## Existing Affected Package

Updating the executable alone cannot reverse a checksum mismatch already present in a package. For the reported package only, the user explicitly authorized a narrowly scoped repair after every other listed file matched its original checksum. The pre-repair SHM, checksum list and completion marker were preserved outside the USB package. Only that SHM entry and the marker's checksum-list digest were updated; conversation data, database/WAL bytes, backup date and run identity were not changed. The local repair audit is private and is not part of this repository.

This is not a generic recovery procedure for checksum failures. A database, WAL, transcript or manifest mismatch must not be accepted by simply rehashing it. Preserve evidence and recover from a trusted source. The app still rejects altered checksummed files.

## Tests and Limits

**97 tests passed, 0 failed, 0 skipped:** 91 core/integration and 6 WPF cases using .NET SDK 8.0.422 on Windows. Isolated app-server tests used `codex-cli 0.163.0-alpha.10.2`.

New tests cover primary indexes, nested indexes and the paginated history database, each with an existing invalid SHM or no SHM. Repeated inspection preserves the complete source file set, hashes and modification timestamps; committed WAL rows remain readable and temporary copies are removed. Another test rejects an active writer. The restore WAL regression now also verifies the original package checksum list after restore.

Production restore was not executed as part of this fix. Synthetic app-server tests are not full Desktop GUI acceptance. Disaster Recovery still replaces selected state; the existing restricted Merge preview still does not support compressed-only or paginated histories. Protect independent local work before replacement.
